# 可用重置最近到期时间消失

## 根因与时间线

- 解析到期时间和面板右侧的文字控件始于 `11f1da6`（v2.0.1，2026-09-24），这次 TPS 和卡片间距调整没有删除它们。以合成的未来日期检查当前布局，文字完整且位于可用重置次数右侧。
- `7dc864f`（v2.3.0，2026-10-23）移除了普通刷新沿用旧到期时间的处理，并增加了按面板可见性、显式请求及提醒开关决定是否查询明细的策略。这避免了依据相同次数错误沿用另一个账号或方案的旧日期，但在面板打开刷新被关闭时，普通刷新会用不含日期的摘要覆盖完整快照。
- 本机设置中“打开菜单栏面板时刷新”为关闭。通过既有 Codex app-server 只读查询验证：不含明细的响应给出 2 次可用重置但没有 `credits` 明细；包含明细的响应有 2 项可用记录且解析到未来到期时间。查询只输出字段是否存在和数量，没有保存或输出原始响应、凭据或账号信息。不能据此确定用户首次观察到消失的具体日期。
- 之前的 TPS/UI 审查没有覆盖“面板打开刷新关闭 + 普通刷新省略明细”这一组合，因而遗漏此回归。

## 修复

- 应用现有刷新策略许可的每次额度查询，默认在同一次 app-server 请求中包含重置明细；没有新增刷新触发，不改变开关或定时间隔。
- 仍直接采用本次响应，服务端没有提供有效到期时间时隐藏文字，不因次数相同而沿用可能属于旧账号或旧方案的日期。失败时继续保留上次成功快照并标为旧数据。
- 保留面板原有字体、间距、配色和原生材质；没有更改重置提醒的启用或投递逻辑。

## 验证

- 新增隔离刷新测试，模拟面板打开刷新关闭，依次执行启动、前台及后台定时查询；测试先因缺失到期时间失败，修复后通过。验证请求均包含明细、每个触发只查询一次，变更或缺失明细时不会沿用旧日期。
- 合成未来日期的浅／深色面板测试验证文字可见、不裁切。真实原生 NSPopover 测试在打开后注入日期，验证文字位于次数右侧，截取了包含箭头的两种外观；展开、返回和反向动画无裁切。截图位于 `build/reset-expiry-native/`。
- 最终 `./build.sh` 和固定证书签名成功；实际执行 `--self-test`、`--settings-self-test`、`--monitoring-ui-self-test` 和 `--session-tps-ui-self-test` 均通过。Command Line Tools 的 XCTest 仅确认编译链接，不能视为已执行。
- 已安装启动修复版，安装版和构建可执行文件的 SHA-256 一致，严格签名校验通过。启动后的本机缓存重新包含 2 次可用重置及有效到期时间；“打开面板时刷新”仍关闭，前台／后台间隔仍为 300／600 秒。未提交、未发布。
- 实体 Touch Bar 和用户正在使用的原生面板没有通过自动化直接操作验收；本次画面验证来自隔离示例数据及实际原生窗口，真实数据链路通过本机查询和安装版缓存确认。
