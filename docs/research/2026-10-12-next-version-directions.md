# 下一版产品方向调研

调研日期：2026-10-12。基线：本地 v2.1.2 README 与当前源码。

本次为公开资料桌面调研，核对了项目说明、功能文档、公开问题反馈及 OpenAI 官方命令文档；未逐个安装竞品。Issue 只证明有人报告过问题，不代表普遍发生率，也不等于当前版本仍有相同问题。以下优先级、工作量与产品方案是针对本项目的判断。

## 产品定位与现有基础

建议定位：面向重度 ChatGPT/Codex 桌面用户的轻量额度提醒与 Touch Bar 操作工具。

两个使用场景应分别设计：ChatGPT 在前台时，Touch Bar 提供额度与操作；用户切去其他应用时，菜单栏和可选通知承担提醒。

当前已具备双窗口剩余额度、重置时间、重置机会到期信息、缓存与过期标记、前后台不同刷新间隔、四槽位自定义及原生菜单执行。当前快捷操作目录包含部分聊天查找、切换、归档等别名，但它们只有实际暴露为原生菜单项时才能被发现。“标记未读”另有当前快捷键绑定执行路径。

因此，缓存、深浅色、原生菜单执行、自定义四按钮都属于已有基础；下一版应增强其使用价值，避免作为新功能重复开发。

## 对标样本

| [OpenUsage](https://github.com/robinebers/openusage/blob/main/docs/settings.md) | 低额度与节奏恶化通知、跨阈值去重、缓存不可用时不通知 | 通知应由状态变化触发，并允许按类型关闭 |

| [Codex Usage](https://www.codexusage.dev/install) | 压力窗口与消耗速度；达到样本门槛才预测；诊断导出 | 预测要有样本门槛；可复用本地额度观测 |
| [Quotix](https://github.com/huakwan/quotix) | 进度条节奏刻度、校验与签名验证后的辅助更新 | 可用简单刻度代替复杂图表；更新体验可分阶段建设 |

| [BetterTouchTool](https://docs.folivora.ai/docs/json/trigger-definitions/) | Touch Bar 长按动作、分组与反馈 | 增加同一按钮的交互层次，不必进一步缩小按钮 |
| [MTMR](https://github.com/Toxblh/MTMR) | 长按、滑动、预设与小组件 | 可借鉴次级动作与预设；复杂脚本配置不适合本项目 |
| [Pock](https://github.com/pock/pock) | 小组件、徽标、媒体手势及系统控制相关配置 | 交互反馈、点击区域与系统控件共存应作为设计约束 |

## 用户痛点与证据强度

1. **不想反复查看余额，又怕任务进行中用尽。** OpenUsage 的阈值通知和 CodexBar 的节奏展示说明这一需求被产品直接覆盖；是否适合本工具用户还需使用反馈验证。[通知文档](https://github.com/robinebers/openusage/blob/main/docs/settings.md)
2. **预测数字可能制造焦虑。** CodexBar 有用户报告重置初期很快被判为超速，过几天又恢复正常。说明“重置初期的短样本外推”容易使人困惑。[Issue #3079](https://github.com/steipete/CodexBar/issues/3079)
3. **不清楚显示的数据是否真的更新。** 有用户报告成本图未刷新，但界面写着刚刚更新；这属于另一数据面板的反馈，不能推导本工具现有额度刷新有同样问题。产品启发是分别显示每类数据的新鲜度。[Issue #3209](https://github.com/steipete/CodexBar/issues/3209)
4. **常驻小工具的性能成本必须可控。** CodexBar 存在高能耗与内存增长报告；不据此断言竞品普遍耗电，而应把子进程启动次数、闲置内存和唤醒次数列为本项目验收指标。[Issue #623](https://github.com/steipete/CodexBar/issues/623)、[Issue #3323](https://github.com/steipete/CodexBar/issues/3323)
5. **按钮存在，不代表当前可执行。** 本项目此前输入框定位、听写失败和候选菜单为空的反馈，是最直接的自身用户证据。优先改进失败解释和功能覆盖，比继续增添不稳定按钮更有把握。

## 方向一：低额、恢复与到期提醒（优先推荐）

场景：用户切离 ChatGPT 后仍希望知道额度何时恢复，或者可用重置机会是否即将到期。

最小版本：

- 5H、周额度分别提供可选低额阈值，例如 20% 与 10%；默认不申请通知权限，用户开启时再申请。
- 每个窗口、每档阈值在一次有效周期内只通知一次。启动时先建立基线，不把旧缓存当成刚发生的跨阈值事件。
- 提供一次性的“恢复后提醒我”。新鲜响应确认该窗口额度恢复后再通知，不仅凭倒计时归零判断成功。
- 区分“5H 已恢复”与“整体可继续使用”：周额度仍为零时，不能承诺已解除所有限制。
- 对最近一次重置机会到期提供可选提醒，使用服务端已报告的时间；到期信息缺失不猜测。

实现：复用 UsageStore 的成功刷新结果，无需增加固定轮询。后台提醒可能受现有五分钟间隔和 macOS 通知设置影响；如需更及时，可在已知重置时刻安排一次刷新，不唤醒睡眠中的机器。

复杂度：中低。主要难点是去重、重启、数据过期与窗口重置识别。验收重点是重复刷新不刷屏、失败缓存不触发恢复提醒。

## 方向二：快捷操作能力与兼容性说明（优先推荐）

场景：用户想用搜索聊天、重命名、置顶等功能，却不知道列表里没有它，是未适配、未绑定，还是当前不可用。

建议把设置中的候选状态分成：可用、需要设置快捷键、当前视图不可用、当前版本尚未支持。执行后的简短失败提示保留，设置窗口提供解释及对应设置入口。这里的状态以打开设置或点击时的检查为准，不能承诺永久准确。

优先验证“搜索聊天、重命名、置顶/取消置顶、复制聊天链接”的稳定执行路径。当前代码已收录部分菜单名称，但只有菜单匹配；下一步是补齐经过验证的内部快捷键路径。不是再次向名称列表添加同名条目。

官方文档确认这些聊天操作存在，且搜索聊天默认没有快捷键，须由用户设置。官方列出功能不代表每个桌面版本都有相同原生菜单或可调用接口。[OpenAI 命令文档](https://learn.chatgpt.com/docs/reference/commands)

实现：原生菜单继续优先；隐藏命令逐个核实稳定标识与当前绑定，复用标记未读的读取方式。仅在前台执行。无绑定或不支持的组合给出说明，不猜测按键。增加脱敏“复制诊断信息”，只包含版本、权限是否可用、命令定位结果和错误类别，不包含路径、菜单完整内容或聊天信息。

复杂度：中。适配维护成本随命令数量增加，建议首批只补三至四项。验收覆盖自定义/清除绑定、语言切换、菜单禁用和前台切换。

## 方向三：四按钮的长按次级动作（最适合 Touch Bar 的增量交互）

保持左侧额度占一半和四个等宽槽位，给普通槽位提供一个可选长按动作。例如短按新对话、长按临时聊天；短按搜索聊天、长按聊天内查找。组合导航槽位首版不再叠加长按，控制学习成本。

按住达到门槛时显示次级动作名称，松手执行；移出按钮或切离前台则取消。主动作在确定为短按时才执行，长按不能同时触发主动作。阈值应通过实体 Touch Bar 小样验证，不能仅凭模拟器设定。

设置预览要明确显示“轻点／长按”。功能默认关闭，不增加背景读取。这是借鉴 BTT、MTMR 的交互方法，不宣称原创。

复杂度：中；工程难点主要是手势冲突、反馈和误触。验收重点是长按不会同时创建两个聊天，常规短按不变慢。

## 方向四：把剩余百分比变成可理解的使用节奏

先在详情面板加两项，而非挤入默认 Touch Bar：

- “最近 30 分钟观察到下降 8 个百分点”；只比较同一额度窗口、有效连续观测。
- “按本周期均匀分配，剩余预算约为每天 X 个百分点”；这是预算参考，不是服务端每天发放额度。

先使用内存中的短期采样，不保存聊天记录。样本不足、跨重置、额度突增、套餐改变、长时间离线时不显示预测。无法识别的账户变化也是连续性风险，因此初版不做跨重启、跨账户长期预测。

“还能使用多少分钟”应后置：即使统计速度准确，下一个任务强度也可能变化。CodexBar 与 Codex Usage 的方案可借鉴，但不能保证具体任务能否做完。[节奏模型](https://github.com/steipete/CodexBar/blob/main/docs/ui.md)、[样本门槛](https://www.codexusage.dev/install)

复杂度：中高。先验证是否帮助用户决策，再建设七天历史图；长期历史会扩大当前24小时缓存与隐私说明的范围。

## 方向五：轻量维护能力

- 手动“检查更新”展示版本和更新内容，打开对应 GitHub Release；先解决发现更新，不急于自动替换自身。
- 导出／导入四槽位配置，包含版本化功能标识与自定义名称，不含账户信息；导入前预览，并对失效命令明确标记。
- 提供两三套可选配置方案，如对话管理、导航；用户主动应用，不自动改写已保存按钮。

Quotix 已有校验、签名与辅助安装流程，可作为后续更新器参考。若自动安装，需要单独的更新包真实性验证与失败恢复设计，现有同源 SHA-256 文件只证明完整性。[Quotix 更新说明](https://github.com/huakwan/quotix)

复杂度：手动检查和配置导出低；可靠自动更新中高。对个人使用收益一般，对公开发布用户更有价值。

## 方向六：新的额度窗口兼容

当前 Models.swift 优先选择 rateLimitsByLimitId 中的 codex，并只识别5小时和周窗口。可先增加诊断提示：数据源是否返回了尚未展示的额度类别；经确认语义后再在详情中列出额外额度。

不同限制不一定共同约束同一任务，不能取所有百分比的最小值就称为“总可用额度”。默认双卡布局无需随接口结构变化自动重排。

复杂度：中，取决于实际返回字段和业务含义。建议作为兼容性研究储备，而非尚无样本时直接立项。Codex Usage 的产品说明已覆盖额外命名额度，可作为需求线索。[产品说明](https://www.codexusage.dev/install)

## 方向七：给本地自动化读取额度（远期）

提供 opt-in、只读 `--status-json`：返回已有快照的额度、重置时间、采样时间与新鲜度。可用于开始长任务前的提醒，AgentMeter 已有同类模式。[AgentMeter](https://github.com/fdtorres1/AgentMeter)

最小实现读取已有缓存，不开启本地 HTTP 服务。不能承诺模型一定遵守预算，也不自动终止工作。只有实际存在脚本或代理使用需求时再做，个人菜单栏使用者的即时收益较低。

## 推荐排期与验收

| 阶段 | 范围 | 价值 | 主要不确定性 |
| --- | --- | --- | --- |
| 建议 v2.2 | 低额／恢复提醒；快捷操作状态说明；验证并补齐少量隐藏命令 | 日常收益明确，复用现有结构 | 不同桌面版本的命令兼容性 |
| 下一轮实验 | 长按次级动作；短期消耗观测 | 提高 Touch Bar 利用率与额度解释性 | 手势误触、统计误导 |
| 公开发布配套 | 手动检查更新、配置导入导出、脱敏诊断 | 降低升级和支持成本 | 对个人用户的需求强度 |
| 需求驱动储备 | 新额度类别、本地只读 CLI | 适配新限制与自动化 | 真实使用需求及服务端语义 |

不建议把多供应商、多账户凭据切换、输入框定位、听写、聊天状态识别或审批按钮塞入同一个版本。前两者明显扩大产品与隐私边界，后几者属于此前已排除或验证不稳定的范围。

建议用一周个人试用评估：通知是否有用及是否重复；候选功能能否解释不可用原因；自定义绑定后操作是否正确；是否保住四槽位点击区域、左半额度与系统控件。性能以当前版本为基线记录请求次数、闲置内存与唤醒次数，不先宣称节电百分比。

若只做一项，建议做“低额／恢复提醒”；若重点发挥 Touch Bar，则做“长按次级动作＋少量已验证的聊天命令”。
