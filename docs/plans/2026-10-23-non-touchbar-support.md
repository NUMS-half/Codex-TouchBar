# 无 Touch Bar Mac 适配计划

日期：2026-10-23。状态：代码与可执行自检已完成，双硬件真机验收待完成；详见[实施与验证记录](../reviews/2026-10-23-non-touchbar-support.md)。以下保留确认后的实施设计。

## 已确认范围

用户选择：本次只适配额度监控，无 Touch Bar 时隐藏专属选项。菜单栏继续承担额度、详情、图表、提醒和设置入口；四个快捷操作仍用于实体 Touch Bar。

硬件范围：仅支持 Apple Silicon（arm64），系统要求 macOS 14+；覆盖有、无实体 Touch Bar 两类机器。

沿用最小改动原则和已批准的 UI。基于当前工作区实施，保留尚未提交的不同套餐适配改动。完成后的默认交付为代码、验证结果和审查记录，不提交、不发布、不替换已安装应用。

## 实施前代码依据

- `AppDelegate.swift:19` 先建立菜单栏，额度刷新、历史与提醒均有独立调用链；`README.md` 也已说明无 Touch Bar 可使用这些功能。因此主要工作是补齐硬件能力隔离及设置适配。
- `AppDelegate.swift:7` 无条件创建 `TouchBarController`；`TouchBarController.swift:424` 起会构造 `NSTouchBar`、额度视图和快捷操作视图。
- `TouchBarController.swift:490` 的显示分支会启动每分钟倒计时计时器，再尝试系统呈现或 Control Strip 回退。`setVisible(false)` 也可能走 Control Strip 隐藏调用。仅在显示入口增加一个判断，不足以覆盖全部路径。
- `SystemModalTouchBar.isAvailable` 只检测 Objective-C 方法，不能证明实体硬件存在；`present` 返回成功目前只代表调用已经发出。
- `SettingsWindowController.swift:110` 的说明、Touch Bar 显示开关、Touch Bar 刷新触发及“快捷操作”页无条件存在，快捷操作控制器也被立即创建。
- `Package.swift` 与 `Info.plist` 要求 macOS 14+；现有发布说明及压缩包名称面向 arm64。CPU 架构与 Touch Bar 存在与否是两个独立条件。

## 目标行为

| 环境 | 额度、图表、提醒 | Touch Bar 运行路径 | 设置 |
| --- | --- | --- | --- |
| 检测到实体硬件，呈现接口可用 | 正常 | 遵循现有显示开关及 ChatGPT 前台条件 | 保留三个页面及原有控件 |
| 检测到实体硬件，用户关闭显示 | 正常 | 不呈现、不运行 Touch Bar 倒计时 | 保留配置入口，便于重新开启 |
| 未检测到实体硬件 | 正常 | 不创建控制器，不调用呈现或 Control Strip 接口 | 隐藏专属控件与快捷操作页 |
| 检测失败或系统呈现接口不可用 | 正常 | 暂停 Touch Bar 路径 | 隐藏不可用操作，通用页给出简短原因 |

无 Touch Bar 时，通用页保留登录启动、启动/面板打开/前台切换/唤醒刷新、前后台定时开关及间隔；另保留“额度提醒”页。手动刷新、通知打开额度或历史、检查更新等入口照常工作。

## 1. 集中处理硬件检测及失败回退

新增小型 `TouchBarSupport.swift`，区分 `present`、`absent`、`unknown`。检测结果仅保存在内存，并提供可注入结果供自检使用。

Apple 的 [NSTouchBar 文档](https://developer.apple.com/documentation/appkit/nstouchbar) 明确说明没有供应用查询硬件是否存在的公开 API；[`isVisible`](https://developer.apple.com/documentation/appkit/nstouchbar/isvisible) 表示内容是否具备显示条件，也不是实体硬件标志。

拟使用项目已有 DFRFoundation 动态加载方式，额外只读查询 `DFRGetStatus`。参考 Hammerspoon 扩展的[原始实现](https://github.com/asmagill/hs._asm.undocumented.touchbar/blob/master/internal.m)：最低位用于识别实体硬件，虚拟 Touch Bar 与实体硬件分开判断。这是私有接口实践，不是 Apple 承诺的协议。

实施规则：

- 通过 `dlopen`/`dlsym` 检查框架和符号，禁止强链接；符号缺失、负数或未识别的状态组合返回 `unknown`。
- 将候选状态 `0/2 → absent`、`1/3 → present` 的转换集中在一个可测试函数；实施首先验证有/无实体硬件两类机器。若真机结果不支持该约定，修正探测实现，不凭方法存在或机型名称猜测。
- 只读取状态，不调用 `DFRSetStatus`，不启动模拟器或修改系统 Touch Bar 配置。不引入机型白名单、设备序列号或新第三方依赖。
- 启动时检测；利用既有唤醒事件及打开设置的动作重新检测。不新增轮询计时器，不把检测放到每次额度刷新中。
- `unknown` 暂用菜单栏，并显示“无法确认 Touch Bar 状态，当前使用菜单栏”；不把它说成确定没有硬件。
- 硬件状态与呈现接口能力分别处理：有实体硬件时，保留完整呈现优先、Control Strip 回退的现有顺序。两条接口路径都不可用时回退菜单栏。
- 检测结果不覆盖 `touchBarEnabled` 等用户偏好；之后检测恢复，按原有偏好恢复功能。

## 2. 按需创建 Touch Bar 控制器

在 `AppDelegate` 中将无条件持有的控制器改为可选、按需创建，由一个集中方法同步硬件状态、用户开关、睡眠状态与前台条件。

- 只有实体硬件已确认、至少一条呈现路径可用且用户允许时，才创建控制器。首次创建时接入现有回调，并应用当前按钮配置和额度快照。
- 额度状态推送只更新已经存在的控制器；使用可选调用时避免 `lazy` 属性在刷新、退出或偏好通知中被意外创建。
- 无硬件或未知状态下，启动、刷新、应用切换、睡眠/唤醒、设置修改、退出等路径均不得创建 Touch Bar 控件、启动其倒计时计时器或登记 Control Strip 项。
- 用户关闭或能力失效时，停止已有计时器，撤下已呈现内容，清理已登记回退项；关闭路径仅清理实际创建的资源。
- 完整呈现和回退各自检查所需的接口。尤其避免“从未登记过回退项，却因 `setVisible(false)` 加载/调用其接口”的现有路径。
- 保留实体 Touch Bar 的 placement `0`、系统控制区、现有两卡和按钮布局。触发重复事件不应重复创建控制器、计时器或登记回退项。

`CodexClient`、`UsageStore`、套餐解析、缓存、历史和提醒算法不需要为硬件类型增加分支。额度的前后台刷新仍取决于 ChatGPT 是否前台，与 Touch Bar 是否启用无关。

## 3. 设置页按能力展示

将同一份支持状态传入 `SettingsWindowController` 与通用页，集中计算可用页面和控件，避免各处自行检测。

- 无硬件时隐藏“显示 Touch Bar”“允许 Touch Bar 刷新按钮查询”及“快捷操作”页；通用页使用“当前使用菜单栏查看额度”等简短说明。
- 未知状态或系统接口不可用时，同样隐藏不可用入口，但说明使用对应原因。无需用户处理的正常无硬件状态不弹警告。
- “快捷操作”控制器延迟到可用页面被访问时创建；菜单栏模式不扫描 ChatGPT 菜单，不请求快捷操作的辅助功能权限。
- 工具栏的 allowed/default/selectable 列表都由可用页面生成；旧调用或诊断若请求不可用的 `.shortcuts`，安全回到通用页。
- 当前页面因能力变化失效时回到通用页；已经建立的快捷操作草稿遵循现有设置会话的保存、取消、关闭规则，不自动保存。临时状态变化不删除已保存配置。
- 保留偏好键名、开关值、四槽位配置及 `.touchBar` 刷新策略值。隐藏只影响当前机器上的可操作界面，不产生配置迁移。
- 通用页使用原有 stack 布局自然收拢隐藏项。保持窗口宽度、颜色、字体、间距规范以及菜单栏 popover 的原生材质和两卡布局。

## 4. 架构范围及文档

本次支持范围明确限定为 macOS 14+、Apple Silicon（arm64）。实现代码仍独立检测 Touch Bar 能力，因为 Apple Silicon 机器也分为有、无实体 Touch Bar 两类。

Intel 不在支持范围内，不安排 x86_64 兼容、构建、依赖核验或真机验收，也不制作 Universal 安装包。构建与分发目标维持 arm64。

更新 `README.md` 的无 Touch Bar 使用步骤、设置页面说明及权限说明；更新 `AGENTS.md` 的项目范围、硬件门控约定和验收要求，并在 `docs/DEVELOPMENT.md` 记录诊断方式。名称、Bundle ID、数据目录及登录项身份保持连续。

## 5. 验证安排

测试使用注入的硬件状态、呈现替身、隔离偏好、临时历史和假通知，不操作真实 ChatGPT，不发送真实测试通知。

| 测试组 | 必须覆盖的行为 |
| --- | --- |
| 检测转换 | 已知有/无实体状态、仅虚拟状态、符号缺失、异常返回；异常归 unknown |
| 生命周期 | 无硬件/未知时创建和呈现调用为零；启动、手动刷新、前后台切换、睡眠/唤醒、退出均安全 |
| 状态变化 | present → unknown → present、显示开关反复切换；资源及时清理，恢复不重复登记 |
| 系统接口 | 完整呈现可用、仅回退可用、全部缺失；均不影响菜单栏初始化与刷新 |
| 设置 | 有硬件三个页面，无硬件两个页面；专属控件隐藏，旧页面请求回退，配置值保留 |
| 业务回归 | 同一合成快照在两类硬件下得到相同菜单栏值、历史与提醒结果；请求失败仍保留过期快照 |
| 套餐回归 | 延续本轮已完成的缺失窗口、Pro 名称和重置次数未知语义，无硬件差异 |
| 外观 | 两类模式的浅/深色设置；完整原生 popover 含箭头，检查两卡、历史导航和长套餐名称 |

关键纯逻辑检查并入 `--self-test`，补充对应 XCTest；硬件模式 UI 检查并入现有 `--settings-self-test`/`--monitoring-ui-self-test`。已有设置诊断应明确注入“有硬件”状态，避免结果依赖运行测试的 Mac。

实施后运行 `./build.sh`、固定证书签名检查、基础自检、设置自检、监控 UI 自检与必要的原生 popover 检查。分别记录 XCTest 是否实际执行、可执行自检结果及真机验收；“编译成功”不等于完成真机兼容性验证。

真机至少覆盖：

1. 一台无 Touch Bar 的 Apple Silicon Mac：正常启动且无 Dock 图标；菜单栏、查询、缓存、图表、提醒设置、登录启动入口正常；无 Touch Bar 专属控件、无辅助功能授权弹窗。
2. 一台有实体 Touch Bar 的 Apple Silicon Mac：现有显示与关闭行为、四按钮、两卡、睡眠恢复和切离 ChatGPT 后撤下均正常，右侧系统 Control Strip 保留。

硬件不足时，将对应真机项明确保留为待验收，不用注入测试冒充真实硬件验证。

## 实施顺序与交付

1. 先核实探测原型与状态转换，补充转换测试。
2. 接入可选控制器与资源清理，验证菜单栏调用链独立。
3. 完成条件设置页和偏好兼容，更新隔离 UI 诊断。
4. 运行回归、检查外观、记录双硬件验收，并更新用户及开发文档。

主要产品改动集中在新增的 `TouchBarSupport.swift`、`AppDelegate.swift`、`TouchBarController.swift`、`SettingsWindowController.swift`；诊断和测试单独存放。

验收标准：无 Touch Bar 的 Mac 可完整使用现有额度监控，且不会进入无效 Touch Bar 运行路径；有 Touch Bar 的 Mac 保留原有体验；硬件检测和系统接口失败不影响额度读取、菜单栏、缓存、历史或提醒。
